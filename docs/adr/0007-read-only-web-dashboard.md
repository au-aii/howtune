# ADR-0007: 閲覧用 Web ダッシュボードを既存 Firebase の読み取りクライアントとして足す

- **ステータス**: 採用済み
- **決定日**: 2026-07-04
- **決定者**: Team 10（ハッカソン後の個人継続: au-aii）

## 背景

HowTune のコア体験（AirPods 頭部モーションでの反応記録・Apple Music 同期）はセンサーに依存するため iOS ネイティブが本体である（ADR-0001）。
一方で「記録した聴き方をあとから振り返る」「アーティスト/レーベルが楽曲のどこで沸いたかを見る」用途は、**大画面で閲覧する Web** の方が適している。

最終的に以下の2つの読者を想定する:

- **リスナー本人**: 自分の反応履歴・お気に入り曲の振り返り
- **アーティスト/レーベル（B2B）**: 楽曲のどこで聴衆が沸いたかの匿名インサイト

これを、既存の iOS / Firebase 構成を壊さずにどう足すかを決める。

## 検討した選択肢

| 選択肢                                                            | メリット                                                                                                    | デメリット                                                   |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **既存 Firebase の読み取りクライアントとして Web を足す（採用）** | バックエンドを作り直さない。iOS と同じ Auth/Firestore を共有。責務が「収集=iOS / 閲覧=Web」に綺麗に分かれる | クライアントが Firestore を読む経路が増える（rules で担保）  |
| Web 用にバックエンドを別途構築                                    | Web に最適化した API を持てる                                                                               | バックエンド二重実装。データ源が二重化し整合性リスク。工数大 |
| iOS 内に WebView でダッシュボード                                 | 配布が iOS だけで済む                                                                                       | 大画面 B2B 用途に向かない。結局 Web 資産が要る               |

## 決定

**Firebase（`howtune-74252`）を単一の真実の源にして、Web は読み取りクライアントを足すだけにする。**

- **責務分離**: iOS = センサー収集・書き込み / Web = 可視化・閲覧 / Firebase = 共通の真実の源
- **接続方式（既存の2経路を踏襲, ADR-0002 / ADR-0006）**:
  - **本人向け（Phase 1）**: Web が Firestore を**直読み**（`how-cards` を `user_id == 自分` で取得）。`firestore.rules` の「how-cards は認証済み read 可」を利用
  - **B2B（Phase 2 以降）**: Cloud Functions で**集計・匿名化**した `song_insights` のみを見せる（生データはアーティストに渡さない。k-匿名性: user_id を含めず、最小人数未満は非表示）
- **技術**: フロント = Next.js（App Router）、認証 = Firebase Auth Web SDK（iOS と同じアカウント）、ホスティング = Firebase Hosting（同一プロジェクトで完結）
- **段階ロードマップ**: P1 本人向け直読み → P2 Functions 集計（B2B 土台）→ P3 アーティスト所有権＋ヒートマップ＋生 `ReactionEvent` 保存

## 結果

- iOS の独自性（AirPods）はそのまま、Web は「読む窓」に徹し、**バックエンドの二重実装を避けられる**
- 既存の書き込み契約（Functions 経由, ADR-0002）と直読み方針（ADR-0006）の延長で一貫する
- B2B では必ず Functions 集計層を挟むことで、個人の反応が特定されない設計にできる
- 既存 `how-cards`（`song_id` + `song_start/end` + `user_id`）がそのまま集計素材になるため、新データなしで第一版に着手できる
- Phase 1 実装は `web/`（Next.js + Firebase）に配置済み。`npm run build` 通過を確認
