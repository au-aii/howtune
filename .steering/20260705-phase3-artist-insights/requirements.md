# 要件定義書 — Phase 3: アーティスト向け B2B インサイト

関連: ADR-0007（read-only Web ダッシュボード）/ `docs/vision.md` / PRD「アーティストダッシュボード」

## 背景

Phase 2 で `song_insights`（匿名・k=5・密度＋推定タグ）を Web で見せられるようになった（`web/src/components/SongInsight.tsx`）。現状は Dashboard が**自分が How カードを付けた曲**しか入口に出さない（`Dashboard.tsx` の `distinctSongs(cards)`）。Phase 3 は **アーティスト/レーベルが自分の楽曲のインサイトを見る B2B サーフェス**を作る。

現状のアクセス制御（`firestore.rules` 確認済み）:

- `song_insights/{songId}`: **認証済みなら誰でも read 可**（`user_id` を含まない匿名前計算）。
- `how-cards`: 認証済み read 可（生データ、B2B には出さない方針）。
- アーティスト・曲所有権の概念は**未実装**。

## 目的・ゴール

- アーティストが「自分の曲」のインサイト（反応密度＋タグ）を閲覧できる B2B 画面を提供する。
- 匿名化（個人の反応が特定されない・k=5）は不変。生データはアーティストに渡さない。

## スコープの分割（重要）

### A. 決定不要スライス（すぐ実装可能・認証/所有権に依存しない）

`song_insights` は既に認証済み全員が read 可なので、**任意の曲のインサイトを閲覧するビュー**は所有権・アーティスト認証を待たずに作れる。

- 例: 曲を指定/選択して `SongInsight` を表示する閲覧ページ（既存 `fetchSongInsight`/`SongInsight.tsx` を再利用、rules 変更なし）。

### B. アーティスト層（設計は本 steering、実装はユーザー判断後）

- アーティストの identity と**曲所有権の証明**、所有曲だけを束ねたダッシュボード、検証バッジ、それに伴う rules。

## 機能要件

- FR-A1（スライス）: 認証済みユーザーが曲を選び、その曲の匿名インサイトを閲覧できる。
- FR-B1: アーティストが自分の楽曲群を一覧し、各曲のインサイトを見られる。
- FR-B2: アーティストは自分が所有権を持つ曲だけを「自分の曲」として扱える（他人の曲を騙れない）。

## 非機能要件

- NFR-Privacy: B2B に出るのは集計済み `song_insights` のみ。個人の `how-cards`/`reaction_sessions` は出さない。k=5 不変。
- NFR-互換: 既存のリスナー向け Dashboard を壊さない（サーフェスを足す）。

## 受け入れ基準

- A スライスは実装＋`npm run build` green＋レビュー用 PR まで。
- B 層は design.md に選択肢と推奨、rules 案が落ち、未決がユーザー判断待ちとして明示。

## オープンな設計判断（ユーザー判断待ち＝実装ブロッカー）

1. **アーティスト認証方式**: (a) 既存 Firebase Auth のユーザーに `role: artist` を付与（手動/招待）/ (b) 別のアーティスト用サインアップ / (c) 配信ディストリビューター連携（将来）。
2. **曲所有権の証明**: (a) 自己申告（`artist_id` を名乗る・低摩擦だが詐称リスク）/ (b) 運営が手動検証して `song_ownership` を付与 / (c) ISRC 等の外部照合（将来）。
3. **`artist_id` のキー**: 既存 how-card は `artist_id`（例 "howtune"）を持つが、これは楽曲メタのアーティスト名由来。所有権をこのキーに紐づけるか、別の検証済み artist アカウントに紐づけるか。
